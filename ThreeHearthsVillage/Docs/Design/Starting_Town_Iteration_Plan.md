## 1. 我建议怎么做

**先做一条居民能实际生活的街，用这条街验证美术、空间、个人视野和需求兑现，再沿街区扩展起始之城。** 地理骨架继续使用现在的第一层；城市内部从重复房屋体量，逐段替换成有用途、有住户、有历史的空间。

最先解决三件事：居民真正走到自己的场所；Kimi 看到这个人的实际视野；一次合理需求能变成可使用的世界变化。美术在这个过程中完成样板，居民的运行反馈决定后续优先级。

本阶段结束时，希望能连续看到这样的过程：居民离家到店里，发现一个具体问题，形成自己的打算，与相关人物交流，提出改造需求；世界暂停完成改造，恢复同一存档，居民走回来使用并评价结果。需求的具体内容由实测产生。

## 2. 当前缺什么，为什么先做这些

| 已核对的现状 | 对迭代的影响 | 对应工作 |
| --- | --- | --- |
| 第一层地理及城镇体量可运行，房屋沿同心街道重复生成 | 鸟瞰有城，人的视角缺少街巷、门口与生活空间 | 固定一段样板街，建立稳定的地块和建筑实例 |
| 房屋批次关闭碰撞；当前相机为自由飞行 Pawn | 走进店里、绕开墙和到达工作台尚无可靠基础 | 行走角色、局部导航、门口和室内交互点 |
| 13 位居民已有持久 ID、人设与故事，其中 3 人已是活跃角色，另外 10 人仍为未激活档案 | 增加 API 调用也不能自动产生真实生活 | 先把三人的生活委托与反馈闭环做实，再分批激活其余居民 |
| `HearthAincradWorldStore` 的 v1 校验限定初始能力、已知地点及 HP | 直接添加成长状态可能无法保存；重开档会破坏连续性 | 显式 v1→v2 迁移，保留原世界和居民身份 |
| 现有看图验证是协调者镜头 | 不能据此证明 NPC 看见了自己的房屋 | 角色眼部截图、个人事实与观察证据绑定 |
| 已有墙、门、石基和分层屋顶构件 | 可以复用，但名称不等于实际拼装尺寸 | 验证真实包围盒、枢轴、接口、UV 和碰撞后组装 |
| 旧系统含国王、税率、国库及皇家目标字段 | 整体接入会把废弃设定带回来 | 提取通用机制，为 SAO 建立独立的输入适配 |

例如，已有名称含 `4m` 的屋顶结构层，其清单包围盒宽约 2.29m。这可能是分片和结构层的设计，执行时要核对完整组合，不能按名称直接拉伸成整栋屋顶。

## 3. 样板街的范围

位置选择**中央广场北缘，沿通往北门的主街**，保留黑铁宫、广场、城门和外部道路的既有地理关系。详细边界在第一单元锁定，后续不因重建预览而随机变化。

首版工程目标如下；这些尺寸与街区安排属于项目补全，不是原作测绘数据。

| 内容 | 首版范围 |
| --- | --- |
| 步行空间 | 约 150m 主街，一条 30–50m 支巷，连接广场边缘和后院 |
| 建筑 | 10–14 个沿街立面，先完成旅店、铁匠铺、木工作坊的可进入一楼 |
| 体量 | 2–3 层为主，窄面住宅、前店后宅、带院作坊组合；上层首版可只做外部 |
| 空间层次 | 连续贴街建筑、小范围退台、侧巷、共享后墙、院墙与后院；变化由用途决定 |
| 生活构件 | 店招、门、窗台、台阶、货架、工作台、少量座椅与货物堆放点 |
| 植物 | 首批一类行道树、一类灌木、一类花草，先形成种植位置与疏密规则 |
| 人物 | 首先激活艾琳、拓真、柏木；其余 10 人保留原档案，不重新生成 |

艾琳的旅店需要临街入口、接待处和短暂停留空间；拓真的铁匠铺需要工作间、收货位置与可通行的货院；柏木的木工作坊需要长料堆放、操作台与不挡路的运输入口。**先让建筑能够支持这些活动，再通过细节呈现人物差异。** 新档案的空间分配属于初始配置，不记作 NPC 自主施工成果。

## 4. 美术目标与制作规则

目标为接近 SAO 动画背景的三维城镇：成年人物比例，清楚的建筑结构，温暖灰泥与石材，陶瓦和蓝灰屋顶，柔和光照及有层次的绿色。原作/Progressive 的来源和取舍沿用 [第一层设计基准](Level0_First_Floor.md)。新增参考要记录出处及具体用途，资料未确认的细节标为项目补全。

| 项目 | 我要落实的做法 | 画面验收 |
| --- | --- | --- |
| 人物尺度 | 以约 1.7m 的成人尺度做首个对照，门窗、台阶和楼高按可用空间确定 | 眼平视角下不会像巨人住玩具房；角色能正常通过门口 |
| 建筑构件 | 地基、墙、门窗洞、楼板、山墙、屋面、檐口、屋脊、附属物分开组合 | 墙接得上，屋顶有合理支承，院落与室内能走通 |
| 屋檐 | 先做好一套檐口截面、厚度、悬挑与转角，再用于不同屋顶 | 近景无悬空、穿插、重复覆盖；远景轮廓清楚 |
| UV | 重复瓦片共享纹理 UV，木石使用统一尺度和可复用纹理条带 | 纹理不随建筑长度拉伸；需要烘焙时单独处理不重叠的光照 UV |
| 材质 | 统一石、木、灰泥、瓦、金属和叶片的参数与纹理尺度 | 消除当前地面明显的格纹感、塑料感和过强反光 |
| 光照 | 固定一套日间基准曝光，先把受光与阴影两侧都调到可读 | 同一机位能公平比较前后版本，不用曝光变化掩盖模型问题 |
| 植物 | 树在有土壤和空间的位置成组；花草靠庭院、窗台与维护区；巷边留通路 | 有树冠、灌木、地被三层，房门和工作路线无遮挡 |
| 城镇差异 | 门面、进深、层数、院落、屋顶方向跟随经营和住户需求 | 不依靠随机颜色或等距摆放来制造丰富度 |

先打磨旅店一栋，再把构件用于作坊和住宅。城墙、转移门与黑铁宫后续逐个做形体校正；黑铁宫目前的黑色穹顶仍只是体量，单有金属材质不足以完成地标复现。

## 5. 执行单元与完成条件

每个单元围绕一个可见结果推进。工程合入后先验证，再开启依赖它的工作；两批工程之间应有真实运行反馈。最初缺少角色与视野的阻断修复可连续完成，但要明确记录尚未具备 Kimi 居民验收条件。

| 单元 | 我要完成的事 | 完成条件 |
| --- | --- | --- |
| S0：同一世界能保存街区 | 增加版本迁移、稳定建筑/地块 ID、住户绑定和局部替换范围；预览不再覆盖此街的持久实例 | v1 可迁移；世界 ID、13 人 ID 和原故事不变；连续两次重启不重建建筑、不重复迁移；坏档和未来版本保留原件 |
| S1：三个人走进自己的地方 | 激活艾琳、拓真、柏木；搭最低限度的碰撞、门口和导航；支持走到、观察、等待和提出需求；接入各人的真实眼部截图及 Kimi | 三人分别从起点走到工作处，墙体不可穿；真实请求彼此独立，目标与截图可追溯；请求失败也能停止当前行动并保留存档 |
| S2：完成旅店美术样板 | 制作一套经验证的构件和材质，完成旅店立面、一楼、门口与首批植物；针对 S1 的真实反馈调整 | 人视角、斜角街景、屋檐近景都通过检查；艾琳能进出；相关变化有个人视野复核 |
| S3：同一构件支持不同用途 | 用样板构件完成铁匠铺与木工作坊的工作空间，保留不同进深、门面和院落；先交付其中一处并验证，再做另一处 | 两种工作路线可用，货物不堵门；拓真/柏木能到达各自工作点并给出基于实景的反馈 |
| S4：一条真实的生活交易 | 实现一条有前置条件的委托流程，例如旅店委托修理工具；委托与答复有明确对象，内容进入当事人记忆；记录物品归属、交付、工序和 Col 收支 | 工具实际移动并被处理；钱与物品账目闭合；中途重启或重放回执不会重复收钱、复制物品 |
| S5：需求进入开发闭环 | 把真实未满足需求形成结构化工单；主持人判断设定、必要性、可复用能力、位置和成本；保存后暂停并锁定施工版本 | 批准只产生待办，不能直接宣称建成；取消、合并、拒绝和等待均有状态；暂停期间不继续执行世界动作 |
| S6：兑现一个新需求 | 从 S5 选出一个最小需求，完成资产或功能，验收后安装到原世界，恢复并让提出者实际使用 | 有提出时的观察、修改前后画面、实际使用记录和居民回访；安装和扣款只发生一次；失败可退回安装前检查点 |
| S7：扩展这套样板 | 按街段替换剩余立面，并分批激活其余居民；每批最多新增 3 位活动居民，先绑定其住所和工作 | 13 位原居民最终都在同一世界活动；新街段有实际用途；并发、存档和通行在增加人口后仍成立 |

S4 的修理委托和 S6 的货架/工作棚都只是可测场景候选。真实 NPC 若提出了更合适的需求，优先实现那个需求；人工设置的测试情境和强制动作必须单独标记，不能记成 Kimi 自发故事。没有合理新需求时，可以让居民继续生活或明确记录“暂无需求”，不刷请求直到模型给出预设答案。

S7 按街段和居民批次拆开交付，不作为一次把全城做完的大任务。它通过后再依次安排：广场地标细化、通往北门的完整街区、城墙与黑铁宫近景。向城外扩展要复用已经通过验证的生活与需求机制。

角色先审核并复用已有骨骼、行走和待机动画，按成年尺度适配；碰撞胶囊可以用于技术测试，但最终生活画面需要可辨识的角色。新增能力只有通过对应验收后才登记为可用，版本迁移本身不能把待实现功能自动开启。

## 6. 每个人怎样思考和看世界

每位 NPC 都有自己的请求、内在故事、记忆和行动队列；统一调度器负责并发与资源，世界主持人负责共享规则和冲突裁决。

**单人输入**包含：永久 ID 与原故事、当前个性与需求、自己的财产和正在进行的工作、亲历或明确被告知的记忆、当前可执行动作，以及本人眼部摄像机在实际位置与朝向采到的一张图。未见过的街区和别人的私有库存不会塞进个人上下文。

**单人输出**区分：看到了什么、哪些只是猜测、想达到什么目标、下一步行动、缺少的能力，以及不确定性。长期愿望可以超出当前能力，但不会直接生成世界事实。人物原始故事保持保存；经历、关系和目标变化通过后续事件追加，避免每次让 API 重写一个新人物。

实际执行遵守以下约束：

- 首次只激活 3 位居民，每位最多 1 个在途请求；之后在现有全局上限内逐步扩展。慢请求不阻止其他人行走与执行已验证动作。
- 请求关联 `world_id`、居民稳定 ID、`observation_id`、场景版本及操作 ID；不以居民数组下标作为跨重启身份。
- 到达并转向后才截图，保留遮挡。相机未看到房屋，就报告看不清或移动观察；不换成协调者鸟瞰图来冒充本人视野。
- 先兼容现有原生 512 像素 PNG、每请求一张图的接口，保存实际眼位、方向、FOV、时间和图片哈希。房屋评价的输入图由 UE 生成；Kimi 返回文字/结构化判断，建模或参考图生成另走资产工单。
- 响应回来后重新检查位置、资源、目标版本和能力。过期或不合法的动作不执行；记录原因，必要时等待合适的新观察事件。
- 个人判断不直接改变共享财产；占用工作台、购买、支付和安装由世界状态原子检查，避免多人同时使用或重复扣款。
- 镜中自我和发型需求放在后续人物外观单元。必须先有真实可见的镜面/自我观察机制，才允许相关图像被用于判断。

普通思考沿用至少 30 分钟现实时间冷却，重启和模拟加速不缩短它。新任务、重要变化及交付回访按既有事件策略去重；改个材质参数、重启场景或同一失败不能成为反复付费的借口。

## 7. 未实现需求如何真正落地

工单至少保存：提出者、触发事件、原始观察、目标对象、期望用途、相关人物、所需能力、设定依据、预计成本和完成条件。状态按下面的顺序推进：

`提出 → 待核实 → 已批准 → 等待实现 → 已验证 → 已安装 → 已使用 → 回访`

驳回、合并、取消和失败可从适当阶段退出，保留理由与历史。模型给出的置信度只是裁决输入；产权、可用空间、材料、能力和世界观约束仍必须检查。新能力应可供同类需求复用，不写成“只有某个 NPC 能触发”的专用分支。

例如，居民可能需要一个能分类存放工具的架子：

1. 先确认他确实遇到收纳问题，以及现有储物能力是否已经能解决。
2. 需要新增时，确定尺寸、位置、存储槽、材料、制作与使用动作，而不只写一句“做个货架”。
3. 保存世界检查点；暂停行动与新收费派发，给在途请求登记状态，迟到响应不得修改暂停或已升级的世界。
4. 完成构件和存储能力，在测试副本验证通行、容量、取放及重复安装，然后作为有版本的交付包进入原世界。
5. 技术安装成功后按规则完成制作/放置和扣款，恢复原档；让提出者实际放入、取出物品，再从自己的位置评价。

物品容量必须对应真实库存，棚子必须有可站立和通行的空间。替换模型要保留原有对象 ID、住户和库存引用。失败时恢复安装前世界状态；费用账本独立持久化，不能跟世界回滚一起退款或重置额度。

## 8. 工程落点与分工

以下标注“拟新增”的模块是职责划分，实施时可根据现有通用代码调整，避免把所有行为继续堆进地图生成器。

| 模块 | 落点及职责 |
| --- | --- |
| 第一层固定地理 | 现有 `HearthAincradFloorPlan`；保留全层节点和连接关系 |
| 地图展示 | 现有 `HearthAincradLevel`；只生成未被持久街区替换的样板及展示，不持有居民全部决策逻辑 |
| 城内持久空间 | 拟新增 `HearthAincradTownLayout`；街段、地块、建筑、入口、工作点、初始绑定及实例版本 |
| 世界保存 | 现有 `HearthAincradWorldStore`；版本迁移、居民活动、财产、工单、冷却与安装记录 |
| 个人生活 | 拟新增 `HearthAincradResidentRuntime`；角色实例、行走、工作状态、个人记忆和可执行动作 |
| 个人视觉与 API | 拟新增 `HearthAincradObservation` / 决策适配；复用现有看图格式、门禁和幂等接口 |
| 世界需求 | 评估复用 `HearthWorldRequests` 通用结构；增加实际审批、安装及使用状态，过滤旧社会字段 |
| 美术资产 | `Art/AincradLevel0/` 下维护源文件、构件清单、组装配方与验证记录；原生资源进入对应 Content 路径 |
